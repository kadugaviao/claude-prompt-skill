## Resposta final

Antes de escrever o prompt, preciso de três decisões. A tarefa apaga dados, e o código não diz qual é o comportamento certo.

O que encontrei: `Cliente.email` não tem `unique` (o comentário no código diz "há duplicados em produção"). `Pedido` aponta para `Cliente` via `@ManyToOne`, então apagar um cliente duplicado afeta os pedidos dele. O login usa `findFirstByEmail` sem ordenação, ou seja, hoje qualquer um dos duplicados pode ser o que autentica. Isso pesa na escolha do registro a manter, porque cada duplicado pode ter uma `senha` diferente.

1. **Qual cliente manter em cada grupo com o mesmo email?**
   - a) O de menor `id` (o mais antigo)
   - b) O de maior `id` (o mais recente, com a senha mais nova)
   - c) O que tiver mais pedidos

2. **O que fazer com os pedidos dos clientes apagados?**
   - a) Passar os pedidos para o cliente mantido (mantém o histórico)
   - b) Apagar os pedidos e seus `ItemPedido` junto com o cliente
   - c) Não apagar clientes que tenham pedidos; só listar esses casos

3. **Onde e como executar?**
   - a) Só gerar um script SQL para você revisar e rodar depois
   - b) Rodar direto no banco local (`jdbc:postgresql://localhost:5432/loja`)
   - c) Preparar para produção: script numa transação, com backup e uma contagem antes e depois

Se você não tiver preferência, vou assumir que dois emails são duplicados quando são iguais depois de `lower(trim(email))`.
