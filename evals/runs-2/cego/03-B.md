**Tipo:** Corrigir bug · **Modo:** plan mode · **Esforço:** padrão

```text
Corrija a LazyInitializationException em GET /pedidos/{id} para que o endpoint devolva o pedido com cliente e itens, sem depender de sessão Hibernate aberta durante a serialização.

## Contexto
Spring Boot 3.3.5, Java 21, Spring Data JPA, PostgreSQL 16. `application.properties` tem `spring.jpa.open-in-view=false`. `PedidoController.buscar` devolve a entidade `Pedido` direto, e `Pedido.itens` é `@OneToMany(mappedBy = "pedido")`, que é LAZY por padrão. O Jackson tenta ler `itens` depois que a transação do `findById` já fechou, e aí a exceção é lançada. Além disso, `ItemPedido` aponta de volta para `Pedido` e não tem getters, então serializar a entidade também ia falhar mesmo com a coleção carregada.

## Insumos
Arquivos a ler:
- src/main/java/com/exemplo/loja/controller/PedidoController.java
- src/main/java/com/exemplo/loja/service/PedidoService.java
- src/main/java/com/exemplo/loja/repository/PedidoRepository.java
- src/main/java/com/exemplo/loja/model/Pedido.java, ItemPedido.java, Cliente.java
- src/test/java/com/exemplo/loja/service/PedidoServiceTest.java

## Tarefa e escopo
1. Crie records em `com.exemplo.loja.dto` para a resposta: pedido (id, cliente, itens) e item (produto, quantidade, preco). Para o cliente, use só identificador e nome, ou os campos equivalentes que existirem em `Cliente`.
2. No `PedidoRepository`, adicione uma consulta que carregue os itens junto com o pedido: `@EntityGraph(attributePaths = "itens")` ou `join fetch`.
3. No `PedidoService`, use essa consulta e converta para o DTO dentro de um método `@Transactional(readOnly = true)`.
4. Faça `PedidoController.buscar` devolver o DTO.
5. Cubra a conversão no `PedidoServiceTest`.
Fora do escopo: o 404 para id inexistente (`orElseThrow()` hoje gera 500) e o endpoint por cliente (`findByClienteId`), para manter a correção pequena. Cite os dois no fim se valer a pena tratar depois.

## Restrições
- Mantenha `spring.jpa.open-in-view=false`, porque ligar esse recurso só esconde o problema e segura a conexão com o banco durante a renderização.
- Não troque o mapeamento de `itens` para `FetchType.EAGER`, porque isso afetaria todas as consultas de `Pedido`, inclusive `findByClienteId`.
- Respeite a separação controller -> service -> repository: a conversão para DTO fica no service e o controller só recebe e devolve DTOs.
- Escreva o teste no estilo do `PedidoServiceTest` atual (JUnit 4 com vintage engine está no pom), porque os testes não sobem PostgreSQL.
```
